# A/B 评测实战示例

## 问题：A/B 评测的两次请求有什么区别？

A/B 对比工具对比的是**两次独立评测的结果**，区别来自于你在两次评测之间**对代码的修改**。

#### 修改方案 A: 优化提示词

```python
# src/incident_classifier_v1.py

# 修改前
prompt = f"""
你是故障严重程度分类专家。

严重程度定义：
- P0: 核心功能完全不可用
- P1: 核心功能明显故障
- P2: 非核心功能故障
- P3: 轻微影响

故障描述：{description}
"""

# 修改后（更详细的定义 + 量化标准）
prompt = f"""
你是故障严重程度分类专家。

严重程度定义（务必准确判断）：

P0 - 灾难级（立即响应）:
- 核心收入功能完全不可用（支付、订单、登录）
- 数据安全问题（泄露、未授权访问）
- 影响 >10% 用户 或 错误率 >10%
- 持续时间 >5 分钟

P1 - 严重故障（1小时内响应）:
- 核心功能部分不可用或严重延迟
- 影响 1-10% 用户 或 错误率 5-10%
- P99 延迟增加 >5 倍

P2 - 中等影响（当日处理）:
- 非核心功能故障
- 影响 <1% 用户 或 错误率 1-5%

P3 - 低影响（可观察）:
- 轻微影响或偶发问题
- 错误率 <1%

故障描述：{description}

请特别注意：
1. 如果描述中提到"支付"、"订单"、"登录"等核心功能，优先考虑 P0/P1
2. 如果错误率 >10% 或影响大量用户，必须是 P0
3. 如果有明确的数字指标，严格按照阈值判断
"""
```

#### 修改方案 B: 调整 Policy 规则

```python
# src/policy.py

# 修改前
def apply_policy(classification: Dict) -> Dict:
    """应用 Policy 规则"""
    severity = classification.get("severity")
    
    # RULE_1: 错误率高估严重性
    if error_rate is not None and error_rate > 10:
        severity = "P0"
    
    return classification

# 修改后（放宽 P0 阈值，增加 P1 判断）
def apply_policy(classification: Dict) -> Dict:
    """应用 Policy 规则"""
    severity = classification.get("severity")
    
    # RULE_1: 错误率阈值
    if error_rate is not None:
        if error_rate > 15:  # 改为 15%（更严格）
            severity = "P0"
        elif error_rate > 8:  # 增加 P1 判断
            severity = "P1"
    
    # RULE_2: 核心关键词强制 P0/P1
    core_keywords = ["支付", "订单", "登录", "注册", "payment", "login"]
    if any(keyword in description.lower() for keyword in core_keywords):
        if severity in ["P2", "P3"]:
            severity = "P1"  # 至少是 P1
    
    return classification
```

## 关键变量总结

### 1. 提示词变量（最常修改）

| 位置 | 变量 | 作用 |
|------|------|------|
| `_initial_classify()` | 初步分类提示词 | 影响第一次分类 |
| `_final_classify()` | 综合分析提示词 | 影响最终分类 |
| 严重程度定义 | P0/P1/P2/P3 的标准 | 核心判断依据 |
| 示例 | few-shot 示例 | 引导模型行为 |

### 2. Policy 规则变量

| 规则 | 当前值 | 可调整 |
|------|--------|--------|
| 错误率阈值 | `> 10` → P0 | 可改为 15、8 等 |
| 核心关键词 | `["支付", "订单", ...]` | 可增删关键词 |
| 降级关键词 | `["已恢复", ...]` | 可增删关键词 |

### 3. 模型变量

| 变量 | 位置 | 选项 |
|------|------|------|
| `OPENAI_MODEL` | `.env` | glm-5.3-flash / glm-5.3-pro / gpt-4o |

### 4. 性能变量

| 变量 | 位置 | 当前值 | 影响 |
|------|------|--------|------|
| `timeout` | `robust_executor.py` | 5s | 工具超时时间 |
| `max_retries` | `robust_executor.py` | 3 | 重试次数 |
| `ttl` | `tool_cache.py` | 300s | 缓存过期时间 |
| `max_workers` | `tool_coordinator.py` | 5 | 并发数 |

## 典型优化场景

### 场景 1: 严重程度判断不准

**现象**: P0 案例被判断为 P2

**原因**: 提示词定义不够清晰

**解决**: 优化提示词，增加量化标准

**预期效果**: P0 准确率从 70% → 95%+

### 场景 2: 类别混淆

**现象**: latency 被判断为 availability

**原因**: 类别定义不够明确

**解决**: 在提示词中增加对比示例

**预期效果**: 类别准确率提升 10-15%

### 场景 3: 边界案例失败

**现象**: 空输入或模糊描述报错

**原因**: 缺少边界处理

**解决**: 增加输入验证和默认逻辑

**预期效果**: 边界案例准确率从 0% → 80%+

### 场景 4: 性能不佳

**现象**: 平均延迟 30s+

**原因**: 无缓存、串行执行

**解决**: 增加缓存、并发优化

**预期效果**: 延迟从 30s → 15s

## 注意事项

### ✅ 做的事

1. **使用相同的测试集**
   - 基线和优化后用同样的案例
   - 保证可比性

2. **一次只改一个维度**
   - 先改提示词，看效果
   - 再改 Policy，看效果
   - 便于定位改进来源

3. **记录修改内容**
   - 保存修改前的代码
   - 记录修改理由
   - 便于回滚

4. **查看新增失败**
   - 不仅看整体改进
   - 也要看是否引入新问题

### ❌ 不要做的事

1. **不要同时改多个地方**
   - 无法判断哪个改动有效

2. **不要用不同的测试集**
   - 无法公平对比

3. **不要忽视新增失败**
   - 修复 3 个，引入 5 个 = 退步

4. **不要只看单一指标**
   - 准确率提升但延迟翻倍 = 不划算

## 总结

**A/B 评测的核心**：
- 两次评测的**测试案例相同**
- 区别来自于**你对代码的修改**
- 对比工具**量化改进效果**

**可修改的变量**（按影响大小排序）：
1. 提示词（影响最大）
2. Policy 规则（影响中等）
3. 模型选择（影响大，但成本也高）
4. 性能配置（影响延迟，不影响准确率）

**推荐优化顺序**：
1. 先看失败分析的建议
2. 优化提示词（成本低，效果好）
3. 调整 Policy 规则（针对性强）
4. 如果还不够，考虑换模型（成本高）
